# Session 3 — Databases with Spring Data JPA

> **Big idea:** You describe your data as Java classes and your queries as interface methods.
> Spring Data + Hibernate write the SQL.

⏱️ ~3 hours · Starting point: end of Session 2 · Ending point: todos stored in a real database (H2, optionally PostgreSQL)

> 🏷️ **Code snapshots:** `git switch -c my-session-03 session-03` gives you this session's starting code. `git diff session-03 session-04` shows everything this session adds.

## 🎯 Learning objectives

1. Explain the stack: **JDBC → JPA → Hibernate → Spring Data JPA**.
2. Map a class to a table with `@Entity`, `@Id`, `@GeneratedValue`, `@Column`, `@Enumerated`.
3. Get CRUD for free from `JpaRepository`, write **derived queries** and **JPQL** with `@Query`.
4. Explain transactions and *dirty checking* (`@Transactional`).
5. Inspect the database in the H2 console and switch to PostgreSQL with a **profile**.

## 🪝 Hook (5 min)

1. Create three todos with curl.
2. Stop the app. Start it again.
3. `curl localhost:8080/api/todos` → `[]`

*"Where did they go?"* They lived in a `HashMap`, inside the program's memory. When the process ends, the memory is freed. We need storage that **outlives the program**.

## 💡 Big idea (15 min)

**Analogy: a translator.** Your app speaks Java (objects, fields). The database speaks SQL (tables, rows).
JPA/Hibernate is the translator sitting in between: you hand it a `Todo` object, and it says
`INSERT INTO todo (title, completed, …) VALUES (…)`.

```
TodoService ──► TodoRepository (interface you write)
                     │  Spring Data generates the class at startup
                     ▼
                 Hibernate (JPA implementation)  ── translates objects ⇄ SQL
                     │
                     ▼
                   JDBC  ──►  H2 (in memory)  or  PostgreSQL (real server)
```

| Java world | Database world |
|------------|----------------|
| class `Todo` + `@Entity` | table `todo` |
| field `title` | column `title` |
| one `Todo` object | one row |
| `@Id Long id` | primary key |
| `@ManyToOne AppUser owner` (Session 4) | foreign key `owner_id` |

## 🛠️ Code-along

### Step 1: dependencies & config

`pom.xml` already has `spring-boot-starter-data-jpa`, `h2`, `spring-boot-h2console` and `postgresql`.
Add to `application.properties`:

```properties
spring.datasource.url=jdbc:h2:mem:tododb
spring.datasource.username=sa
spring.datasource.password=
spring.jpa.hibernate.ddl-auto=create-drop
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
spring.h2.console.enabled=true
```

> 💡 `show-sql=true` is our "make the hidden visible" switch: every SQL statement Hibernate runs is printed.

### Step 2: record → entity (I do)

JPA entities **can't be records**: Hibernate needs a no-argument constructor and must be able to change fields.
Turn `Todo` into a class. Add `description` and `priority` while we're here:

```java
public enum Priority { LOW, MEDIUM, HIGH }
```

```java
@Entity
@Table(name = "todo")
@Getter @Setter            // Lombok generates getters/setters at compile time
@NoArgsConstructor         // required by JPA
public class Todo {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // DB auto-increments the id
    private Long id;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(length = 500)
    private String description;

    private boolean completed;

    @Enumerated(EnumType.STRING)          // store "HIGH", not 2
    @Column(nullable = false)
    private Priority priority = Priority.MEDIUM;

    @Column(nullable = false, updatable = false)
    private Instant createdAt;

    public Todo(String title, String description, Priority priority, Instant createdAt) {
        this.title = title;
        this.description = description;
        this.priority = priority == null ? Priority.MEDIUM : priority;
        this.createdAt = createdAt;
    }
}
```

> 🔮 **Predict:** We use `EnumType.STRING`. What would go wrong with the default (`ORDINAL`, which stores 0, 1, 2)
> if someone later adds `URGENT` at the *start* of the enum? (Every existing row silently changes meaning!)

### Step 3: the magic moment, delete your repository code (We do)

**Delete** the whole in-memory `TodoRepository` class and replace it with:

```java
public interface TodoRepository extends JpaRepository<Todo, Long> {
}
```

That's it. An interface with **no body**. Start the app and watch the console:

```sql
create table todo (
    id bigint generated by default as identity,
    title varchar(100) not null,
    ...
)
```

> 🔮 **Predict:** `TodoService` calls `findAll()`, `findById()`, `save()`, `deleteById()`. Will it compile?
> Yes! We chose those names in Session 2 on purpose. The only edits are `todo.title()` → `todo.getTitle()`
> (entities use getters) and the new constructor. **The service didn't care where data lives.** That's DI paying off.

### Step 6: queries without SQL, i.e. derived queries (We do)

Spring Data reads the **method name** and writes the query:

```java
public interface TodoRepository extends JpaRepository<Todo, Long> {

    List<Todo> findByCompleted(boolean completed);

    List<Todo> findByTitleContainingIgnoreCase(String text);

    List<Todo> findByPriorityOrderByCreatedAtDesc(Priority priority);

    long countByCompleted(boolean completed);
}
```

| Method name piece | Becomes |
|-------------------|---------|
| `findBy` | `select … where` |
| `Completed` | `completed = ?` |
| `TitleContainingIgnoreCase` | `lower(title) like lower('%' + ? + '%')` |
| `OrderByCreatedAtDesc` | `order by created_at desc` |
| `countBy…` | `select count(*) …` |

Wire `GET /api/todos?completed=true` and `GET /api/todos/search?q=milk` to these. Watch the SQL in the console.

### Step 7: when the name gets silly, use `@Query` (JPQL)

```java
@Query("""
        select t from Todo t
        where lower(t.title) like lower(concat('%', :text, '%'))
        order by t.createdAt desc
        """)
List<Todo> searchByTitle(@Param("text") String text);
```

JPQL uses **class and field names** (`Todo`, `t.title`), not table and column names.

### Step 8: transactions & dirty checking (I do, with a 🔮)

Add `update` to the service:

```java
@Transactional
public Todo update(Long id, UpdateTodoRequest request) {
    Todo todo = findById(id);
    todo.setTitle(request.title());
    todo.setCompleted(request.completed());
    return todo;   // ← no save()!
}
```

> 🔮 **Predict:** There's no `save()` call. Will the change reach the database?

Run it and watch the console: an `update todo set …` appears. Inside a transaction, Hibernate keeps an eye on every
entity it loaded (*dirty checking*) and writes the changes at commit.

**Transaction analogy:** a bank transfer. Debit and credit happen *together* or *not at all*. `@Transactional` on
the service means "everything in this method is one unit of work". Put it on the class, and use
`@Transactional(readOnly = true)` on read methods (see the finished [`TodoService`](../src/main/java/org/todo/spring_todo/todo/TodoService.java)).

### Step 9 (optional): a real database with PostgreSQL

```bash
docker compose up -d                                         # starts PostgreSQL on port 5433 (see compose.yaml)
./mvnw spring-boot:run -Dspring-boot.run.profiles=postgres  # loads application-postgres.properties on top
```

Create todos, **restart the app**, and they're still there. That's what we wanted in the Hook.
Same Java code, different database: only configuration changed.

## 💥 Break it on purpose

| Change | What you'll see | Lesson |
|--------|-----------------|--------|
| Remove `@Id` | *No identifier specified for entity* | Every entity needs a primary key |
| Remove `@NoArgsConstructor` | *No default constructor for entity* (when loading) | JPA creates objects empty, then fills fields |
| Rename a method to `findByTitel(String t)` | App won't start: *No property 'titel' found for type 'Todo'* | Derived queries are checked **at startup**. Typos fail fast. |
| Name the entity table `user` | SQL syntax error | `user` is a reserved word (that's why Session 4 uses `app_user`) |
| Remove every `@Transactional` from the service (class *and* method) | `update` returns the new title, but a fresh `GET` shows the old one |  Dirty checking only works inside a transaction |
| Set `ddl-auto=validate` | *Schema-validation: missing table [todo]* | `validate` checks but never creates. Production apps use migrations (Flyway). |

## ❓ Quiz

1. What's the difference between JPA and Hibernate?
2. You wrote `interface TodoRepository extends JpaRepository<Todo, Long>`. What do `Todo` and `Long` mean?
3. What SQL would `findByPriorityAndCompleted(Priority p, boolean c)` produce, roughly?
4. Why did the `update` method work without calling `save()`?
5. Why don't we return `Todo` entities straight from the controller?

<details><summary>Answers</summary>

1. JPA is the **specification** (the rules and the annotations); Hibernate is an **implementation** of it (the code that does the work).
2. The entity type and the type of its `@Id`.
3. `select … from todo where priority = ? and completed = ?`
4. Dirty checking: inside a `@Transactional` method Hibernate tracks loaded entities and flushes changes on commit.
5. It couples API shape to DB shape, can expose sensitive fields, and can cause lazy-loading/serialization problems. DTOs give you control.
</details>

## 🧭 Recap

- `@Entity` maps a class to a table; `JpaRepository` gives CRUD for free; method names become queries.
- `@Transactional` makes a method all-or-nothing and enables dirty checking.
- Configuration (profiles) decides *which* database; the Java code doesn't change.
